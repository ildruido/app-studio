# Section 9: repo settings that protect `main`

_On-demand reference, part of [GOVERNANCE](../GOVERNANCE.md). Read it when you change CI, the tier rules, the branch gate, the merge queue or the owner OK._


Set by the Admin once in GitHub (Claude can't change repo settings) and checked on 2026-11-10 by a test PR that stayed blocked until `check` went green. Auto-merge is on since the rule switch (2026-11-15): the tier (below) decides which PRs wait for the App-Studio Owner's OK.

- **Settings → General → Pull Requests:** only "Allow squash merging" ticked; "Automatically delete head branches" ticked; "Allow auto-merge" ticked (the Admin's click at the rule switch). Until it is ticked, threads merge a green PR directly.
- **Settings → Rules → Rulesets → "main protection":** enforcement Active, empty bypass list, target the default branch, rules: restrict deletions, block force pushes, require status checks to pass with `check` (GitHub Actions) and "up to date before merging". No "require a pull request" rule, so Claude can still push its branch.
- `check` is skipped on a draft, so a draft PR can never merge; `finish` opens every PR as a draft and marks an internal one ready at once (section 5).
- **Branches of closed, unmerged PRs are not deleted automatically**, and Claude has no tool to delete them: ask the Admin for the "Delete branch" click, or avoid test PRs that end unmerged.
- **The owner OK label:** GitHub doesn't offer required reviewers on environments for this private repo, so there is no tap Claude can't press. Instead `check` fails for a PR in the owner tier until it carries the label `owner-ok`. A thread adds that label only after the App-Studio Owner's OK in the thread, and adding it records a fingerprint of the PR's own changes (a comment by CI; `scripts/own-fp.mjs`, which leaves out the release record, `CHANGELOG.md` and the plugin version and uses zero context lines, so merging `main` never changes it). The OK stays valid while that fingerprint is unchanged, so updating the branch because `main` moved keeps it; CI removes the label when the PR's own changes differ, and then the OK has to be given again. It stops mistakes, not a deliberate bypass (tested on PR #51). If the repo ever gets a plan with environment reviewers, replace it with a required reviewer.
- **The branch live-check gate:** step `gate` in the `check` job runs `scripts/branch-gate.mjs` from `main`. For a PR that changes app-facing files it reads the results on studio-scratch PR #72 with a read-only token (repo secret `LIVE_CHECK_TOKEN`, set once by the Admin) and fails unless a result passed every scenario named in the record's `checks.branch` for the PR's current fingerprint. Results come from the runner's code, never typed by the build thread; if #72 can't be read, the gate fails closed. A loader or setup release also fails if its record is not `pending`. Internal-only PRs never touch it. The gate and the tier rules it sits in (`scripts/branch-gate.mjs`) are the owner tier.
- **The merge queue:** workflow `merge-queue` (`scripts/merge-queue.mjs`, from `main`, no PR code) queues only the open PRs to `main` that need a studio-scratch branch live check: they change app-facing files and their release record names branch scenarios (an unreadable record counts as yes). Every other PR, internal or with a record that names no branch check, never waits and merges as soon as CI is green. Order: PRs labelled `queue-first` first (a fix the live check or the gate itself needs, so it never waits behind the PRs that need it; after adding the label to a draft, start the `merge-queue` workflow by hand), then ready PRs, then drafts, each oldest PR number first, so a stalled draft never holds up a ready PR; any PR can be added with the label `queue`, and removing the label from an app-facing PR changes nothing. It comments `QUEUE-WAIT` (who is ahead) or `QUEUE-TURN` on the PR, again whenever that changes (a PR that is overtaken gets a new `QUEUE-WAIT`, and `QUEUE-TURN` when it is first again), which its build thread is subscribed to, and switches on auto-merge for the first PR once it is ready. Step `queue` in the one `check` job (it also runs the script's `run`, so every PR event posts the comments) fails a queued PR that is not first, so a PR cannot merge out of turn; when the one ahead merges or closes, the next PR's thread updates its branch from `main` and that push reruns `check`. Comments and auto-merge made with the workflow token start no CI run, so the workflow cannot update the branch itself, and the `merge-queue` workflow itself runs only when a PR opens, reopens, closes unmerged or becomes a draft (CI skips drafts), when `main` moves (a merge hands the turn on) or by hand, because every run is billed as at least one minute (issue #339: no cron, no run per finished CI). Whenever `main` moves (a release-record PR or another PR outside the queue merges) and the first PR is behind it, the same run posts one `QUEUE-UPDATE` comment on it per `main` commit, so its thread updates the branch without a person nudging it. A stalled PR holds the queue until it is closed. GitHub's own merge queue is not offered for a private repo on a personal account. Small related changes share one PR and one run.
- **Risk tier:** `scripts/tier.mjs`, run inside `check` as it is on `main`, sets each PR's tier from the paths it changes (owner tier, live check before apps, or auto), prints it on the run's summary, and sends unknown files to the owner tier. A thread can only raise a tier, with the label `tier:owner`. For `docs/GOVERNANCE.md` and `docs/studio-project-instructions.md`, a diff check lets wording-only edits through (at most 30 words, no rule word or number, no heading, list item or table row added, removed or moved). The tier decides who merges (section 5): the App-Studio Owner's OK for the owner tier, auto-merge for the rest.
- **A PR can't change how it is judged:** `.github/workflows/ci.yml` runs only from `main` (`pull_request_target`; CI is two jobs, `tests` and `check`, billed as at least a minute each, issue #339), so a PR's own edit of it has no effect until it is merged, and any change under `.github/` is the owner tier. The tier and release check run the scripts as they are on `main`; the PR's code runs only in the `tests` job, which has a read-only token and no secret; the `check` job holds the write token and the live-check secret and runs only scripts from `main`. `scripts/ci-guard.test.mjs` fails if that split is broken. This does not stop someone with push access who adds a second workflow of their own that reports a `check`: the tier and label are a tripwire against mistakes, as above.
- **Off switch:** Settings → Secrets and variables → Actions → Variables → New repository variable `ALL_NEED_OWNER` = `true` sends every PR to the owner tier; delete it to turn the tiers back on.
