# Section 5: building a change

_On-demand reference, part of [GOVERNANCE](../GOVERNANCE.md). Read it when you build and release a change; `node scripts/finish.mjs next` prints each step, so this is the background._


- **One thread per issue** (or per small group of related issues), on the standard thread model. The review model only for risky designs, or after a thread fails twice; the strongest model only when the App-Studio Owner or a plan asks for it ("Models" in [harness.md](../../plugins/studio/skills/harness-sync/harness.md) maps each role to a model).
- Read the issue, this file, the README and the files involved before changing anything. Don't re-derive what an issue or the handover already settled.
- **Keep the core generic:** app facts go in an app's App profile, stack facts in a stack pack. `node scripts/core-lint.mjs` must pass.
- **Checks before a PR:** `node --test scripts/studio-sync.test.mjs`, `node scripts/core-lint.mjs`, `node scripts/coherence-lint.mjs`, and `node scripts/packs-smoke.mjs web artifact` when a pack changed. The required `check` runs all of these on every ready PR, plus `node scripts/release-check.mjs --base origin/main`, which fails when harness files changed without the PR's unreleased entry, when the plugin version moved outside a release cut (or a cut left an entry behind), or a pack changed without its own version bump. Working practice, not a gate: a fix comes with a test that fails without it, and the reviewer looks for one; code checks only that the tests pass.
- **Skills:** a new skill, or a change to a skill's description or behaviour, is drafted and checked with Claude's account skill `anthropic-skills:skill-creator` (tune the description, run a few test prompts). The PR hand-over says what was tested. Typo and wording-only fixes are exempt. The key skills (`build-feature`, `new-app`, `harness-sync`) also get a deeper check: a few more test prompts covering their main paths. skill-creator is not copied into the repo; if it isn't available in the session, the thread stops and tells the App-Studio Owner. The studio-scratch live check (section 7) stays as it is.
- **Coherence review:** after a change to this file, a skill, the app template or the coordinator routing, the coordinator or thread proposes a coherence review (`docs/COHERENCE-REVIEW.md`, skill `coherence-review`) in one line with its rough cost. It runs only after the App-Studio Owner says yes; it is never scheduled.
- **After the build, run `finish`** (`scripts/finish.mjs`, tests `scripts/finish.test.mjs`). Every post-build step is code, the same each time; only results vary. The thread gives only what needs judgement, once, to `node scripts/finish.mjs start`: the issue(s), a Conventional Commit title, a short summary phrase, what changes for the App Creator, numbered **App action** and **Admin action** steps if any, the branch (and for a loader or setup release, main) scenario ids from `releases/scenarios.json` (or `--no-branch-check "<reason>"`), what wasn't verified, and the PR's attribution lines (`--release-now` when this PR must also cut the release: an urgent fix, or the App-Studio Owner asked). Then it runs `node scripts/finish.mjs next` and makes exactly the calls it prints, until it prints DONE. It never decides a step itself, and reports status only from `node scripts/finish.mjs status`. What the code does:
  - **Unreleased entry, no version:** writes `releases/unreleased/<id>.json` (the same fields as a release record, plus the bump it asks for: PATCH by default, `--minor` for a new skill, agent, hook, profile field or workflow change) and a raised version for each changed pack. The plugin version and `CHANGELOG.md` stay as they are, so parallel PRs never collide on them. `node scripts/release.mjs unreleased` lists what is waiting.
  - **The release cut** (`node scripts/finish.mjs release`, on a branch that holds nothing else; about weekly, or when the App-Studio Owner asks): takes the next free version, folds every waiting entry into one `releases/<version>.json` (its `changes` list), raises the plugin version and renders `CHANGELOG.md` (by `release.mjs`; nobody and no model edits it; releases up to 0.36.2 are frozen in `docs/CHANGELOG-legacy.md`), then follows the PR like any other. It refuses while an entry's `main` check is pending, and rebuilds itself when `main` moves, so a change that merged meanwhile is always in the record. When a `main` check failed, its entry stays pending and blocks every cut (`--release-now` too): the fix is a new PR with its own `main` check, and once that passed, `node scripts/release.mjs pass-main <the failed entry's id>` in a small PR clears the old entry. A merged change is taken back by reverting its files in a new PR, never by deleting its entry. The commit that adds a record therefore holds exactly that release, which is what apps pull.
  - **Kind and live check need:** from the files changed, with the same lists CI uses: internal (no scratch run), app-facing (a branch check) or loader/setup (a branch and a `main` check; its entry says `status.main` `pending`, and no release is cut until the main check passes).
  - **Checks:** runs the CI tests job's checks locally (read from `ci.yml`, plus the packs smoke test when a pack or the sync tool changed and the release check), merges `main` in, commits and pushes.
  - **PR:** opens it as a draft always (drafts skip CI, so CI runs once, when the PR is marked ready: at once for an internal change, after the branch live check for one apps get), with the attribution, `Closes #<n>` and a hand-over (what changed, how to test, the live checks, **what wasn't verified**); records the PR number; subscribes and schedules the 3-minute check-in.
  - **Live check** (section 7): waits for the merge queue's `QUEUE-TURN`, requests the branch check, reads the result (CI's relay comments it on the PR; the thread never copies one), marks the PR ready on a pass; after the merge, runs the `main` check when the entry names one and opens the small `pass-main` PR.
  - **Merge by tier** (section 9; `tier.mjs` as it is on `main`): green and mergeable merges now; otherwise auto-merge (squash). In the owner tier it prints the one-line OK request to post. After the App-Studio Owner's OK in the thread, the thread runs `node scripts/finish.mjs owner-ok`, and the code adds `owner-ok`. If CI later drops the label because only `main` or the version moved, the code adds it again without asking; it asks again only when the PR's own changes changed.
  - **Follow-up:** red CI, a failed live check or a merge conflict in the thread's own files are the only things handed back to the thread to fix (then `node scripts/finish.mjs push --message "fix: ..."`). The thread unsubscribes when the code says DONE and hands back the status.
- **Scenarios, written first** (`releases/scenarios.json`): each live check is one catalog entry (id, title, `branch` or `main`, a `kind`: `script` (fixed `steps` that code runs itself in the scratch app, no model; use it whenever the check only runs commands and reads what they print or leave behind) or `thread` (the default: the prompt studio-scratch runs (the runner can only act in its own thread or a helper agent, never a fresh thread)), and pass rules that code reads on GitHub: PR state, checks, files, expected output, never Claude's summary). Working practice, not a gate (nothing can check the order): the build thread writes or updates the scenario before the code, next to the failing unit test, and a new scenario is not first run red on `main`. The entry names only the scenarios that change needs; only those run. Floor, enforced by `finish start` and `release.mjs validate`: an app-facing change names at least one branch scenario or `none` with a reason; a loader or setup change also names at least one `main` scenario.
- **Who merges, by tier** (CI sets the tier from the files the PR changes and prints it on the run):
  - **the owner tier** (the loader, the setup script, CI and the tier rules, unknown files, a rule file unless only its wording changed, a lost test, a changelog **App action** or **Admin action**, more than about 400 lines): only after the App-Studio Owner's OK in the thread. The OK covers the PR's own changes, never a later change to them.
  - **Every other tier** (what apps get, other docs, added tests, the changelog): merged when `check` is green, never around a required check or approval. A PR that apps get cannot merge before its branch check passed, and apps get it only with the next release, which is not cut before any `main` check passed.
  - A thread can raise a PR's tier with the label `tier:owner`, never lower it.
