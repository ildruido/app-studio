# Live-check runner

How a live check runs without anyone pasting prompts between Projects. All logic is in `scripts/live-check.mjs` (tests: `scripts/live-check.test.mjs`); Claude only acts out each scenario prompt and does the platform actions. Scenarios are in `releases/scenarios.json`; a release's record names the ones it needs.

**Mailbox** (draft PRs in `studio-scratch`, never merged or closed): **#71 = requests**, **#72 = results**. A message is a PR review with event COMMENT (plain comments don't wake a session). One session per PR receives events.

## Build thread (app-studio) asks for a check
`node scripts/finish.mjs next` does every step by code (GOVERNANCE section 5): it waits for the merge queue's `QUEUE-TURN`, updates the branch from `main`, makes the request with `live-check.mjs request` (with `fp:`, the fingerprint of the PR's app-facing changes, which CI's branch gate matches), and prints the calls to make: the review (COMMENT) on studio-scratch #71 and a 60-minute check-in. The thread never carries a result: the `merge-queue` workflow runs `scripts/live-check-relay.mjs` (half-hourly and on PR events), reads #71 and #72 with the read-only token, and comments each new result on its PR as `<!-- live-check-result:<id>:<pass|fail> -->` plus the result text (a branch run goes to the open PR on the request's branch, a main run to the PR the release record names). That comment wakes the thread; `finish next` reads only the marker from the facts: a pass marks the PR ready, a fail is handed back, no result by the check-in counts as failed. After the merge, for a loader or setup release or a record that names main scenarios, it does the same for a `main` check and opens the `pass-main` PR.

## Runner thread (studio-scratch) does a check
1. (If `prepare` says "unknown scenario" because the checkout is behind, first run `git -C <app-studio checkout> fetch origin <branch> && git -C <app-studio checkout> checkout --detach <commit>` and run it again: a new scenario exists only in the commit under test. Since 0.39.5 `prepare` moves the checkout before it reads the catalog.)
1. `node <app-studio checkout>/scripts/live-check.mjs prepare --request <file> --app <this app>`: takes the one-run lock (busy: answer with `result --failed "runner busy"`), moves the app-studio checkout to the commit, resets the app, syncs it, and lists each scenario prompt.
2. Act out each prompt in this thread (or a helper agent; the runner cannot open a fresh thread, so no scenario may need one). **Run every scripted command through the wrapper**: `node <app-studio checkout>/scripts/live-check.mjs exec --outputs <dir> --scenario <id> --step <name> -- <command...>` (the prompt names the steps). Code runs the command and saves its exit code, stdout and stderr to `<dir>/<id>/<step>.json`; the `exec` and `exec-absent` pass rules read only those files, never your summary. You choose which step to run next, not what it printed. Then save each final text to `<dir>/<scenario id>.txt`: your `RESULT <id>: PASS|FAIL` line is only a cross-check (if it disagrees with the code's verdict, the run fails with "disagreement"). A scenario marked `model-behaviour` tests what Claude says or sees, so its text is the evidence.
3. Read the raw GitHub state a scenario's pass rules name (PR state, checks, files) into a `facts` file; paste the raw API response, never a summary of it. Then `judge --request <file> --outputs <dir> [--facts <file>] [--app <this app>]`.
4. `result --request <file> --verdicts <file>` (or `--failed <reason>`) prints the result; post it as a review (COMMENT) on #72. It frees the lock.

## Start prompt (the Admin pastes it once into a new studio-scratch thread; again only if the runner thread ends)
> You are the live-check runner for app-studio. Subscribe to pull request 71 in this repo (`subscribe_pr_activity`) and do nothing else until a review arrives on it. Each review whose text contains `LIVE-CHECK-REQUEST` is a request: save the review text to a file and follow `docs/LIVE-CHECK-RUNNER.md` ("Runner thread") in the app-studio checkout, run from this app. Post the result as a review with event COMMENT on pull request 72. Never merge or close pull requests 71 or 72, never change app-studio, and never answer anything that is not a request.

## CI reads the result
Two CI jobs read #72 with the same token: the relay above (comments the result on its PR) and the merge gate below (judges the merge).
CI's `gate` job reads reviews and comments on studio-scratch #72 with a read-only token (repo secret `LIVE_CHECK_TOKEN` on app-studio: a fine-grained token, only the `studio-scratch` repo, permission Pull requests: read). It looks for a `LIVE-CHECK-RESULT` with `verdict: pass`, the PR's `fp`, and every scenario in the record's `checks.branch` as PASS.

## One-time manual check: helper agents run on the model they declare (#250)
The runner can't load new agent definitions mid-thread, so this one is run by hand, once, after the release (the branch scenario `subagent-model-logged` only proves the log line works). Open a **fresh** studio-scratch thread after the release is on `main`, and send:
> Run `harness-sync`, then start the `qa` helper agent with the task "Reply with the word ready and use no tools", and wait for it to finish. Then run `tail -n 8 /tmp/studio-hooks.log` and show me the output.

Pass: the log shows a line `subagent qa model=claude-sonnet-… effort=medium`, while the thread itself runs on another model (Opus). Fail: `model=unknown` (the log step can't read the transcript) or an `opus` model on that line (the pin was ignored); hand back the log lines. Skills stay `model: inherit` until this passes; a later change then pins them and checks the same way.
